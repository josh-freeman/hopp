# Hopp MVP implementation and handoff

Resumed 2026-09-13 from Claude session `d9b722cc-c905-4ede-8387-8ec9e6fa26f6` after its usage limit. The original multi-agent plan workflow did not produce a final assembled plan. The approved design, mockups, research and original API captures were preserved and implementation proceeded in the bounded workstreams below.

**Goal:** Ship a static, phone-friendly Swiss journey planner that offers a researched sprint shortcut only when it leaves the full margin and beats the regular connection's arrival.

The implemented optional Google/profile API extends the existing website backend. **Its production deployment is pending because Fly builders rejected overdue billing; Hopp endpoints currently return 404.** The isolated demo profile remains usable. ## Decisions made while implementing

- The final user-selected default is **3.5 m/s**. Recomputed reference times replace obsolete 3.3 m/s examples. Margin configuration affects the model. UI spare means time left **after** sprint and margin.
- Research confidence is not field verification. Uncertain high-confidence route flags were lowered; missing landings are reported, never invented. Geometry and deliberately incomplete platform coverage remain visible in validation output.
- Candidates must begin with a rail journey at the shortcut station. Known missed onward transfers disqualify candidates. Unknown/ambiguous platforms never produce a GO.
- The live screen pins the selected scheduled service. Another train becoming catchable does not silently replace it.
- Explicit **Start sprint** distinguishes a rider who passed the stop from a runner already off the tram. The platform button is self-confirmation; it is not GPS boarding verification or an accepted competitive attempt.
- Mobile emulation is evidence for viewport and engine behavior, not a claim that every physical iPhone, Samsung Internet version, keyboard or home-screen installation has been tested.
- The map is prominent in Results before the longer directions. Bundled area maps show researched stop, station and platform context; they do not claim indoor turn-by-turn positioning or verified entrance availability.

Offline service-worker support, automatic route promotion, actual commuter timings and any GPS journey verifier remain future work. Shared accounts, practice/daily-use points and profile-card unlock graphics are implemented in source; they supersede the old Worker/D1 proposal. Real account rollout awaits Fly billing resolution and API deployment. Strava import, derived pace calibration and rewards are deferred under the June 2026 API Policy.

## Expanded route research and copy corrections

The current catalogue has 11 enabled records and one Lausanne draft. Nine records were added after source checks across 40 stations: 25 approaches investigated in detail and 38 nearby-stop observations in a broader timetable screen. The [expansion report](../../research/2026-09-13-route-expansion.md) links exact sources, raw captures, public path chains and rejected alternatives. The real Winterthur Archstrasse → Aarau example is covered by both engine and browser regressions.

New hack files enter the bundle automatically through `scripts/build-catalogue.ts`. Partial platform coverage is allowed and tested; missing platforms stay unavailable. Bus feeders use bus stationboards, and origin-start routes no longer tell someone to get off a tram.

Removed the earlier generic tagline and marketing copy. Later explicit user direction restored the chosen lead “the art of being on time” with “Train shortcuts for runners.”; interface graphics use SVGs rather than emoji. Early-alighting guidance leads with **GET OFF EARLY AT**, relative to the regular station stop. Removed browse-all route discovery. Route notes and source links now belong to the specific searched trip. Maps and directions use the selected route's actual stop, station and supported platform. Sources expand inline without another required screen.

Final integration review fixed origin-only timing, fallback walking readiness, preservation of the selected train on confirmation, and automatic expiry of visible GO offers. The planner remains bounded to the earliest matched opportunity and one station candidate search; it does not claim to exhaust every possible route through every station.


## Simplified flow and demo

The user requested fewer screens, a more prominent map and more deliberate design and typography. Results now carries the route map, timing, directions and fallback together; Go live is the only primary continuation after search. Legacy try, route, detail and shortcut hashes resolve to Results. The phone preview and screenshot matrix expose Plan, Results, Live, Settings, On the platform and Profile: six screens across sixteen viewport classes, producing 96 screenshots.

The demo player at `/hopp/demo.html` and MP4 at `/hopp/demo.mp4` show the actual browser UI with labelled synthetic times. The 40.04-second clip continues from Live into the isolated demo profile, awards 25 practice points and ends after selecting Forest; it never starts an actual sprint or uses a real account. Recording and export instructions are in the project README. Automated verification totals are maintained in `docs/qa/README.md`; they do not replace physical-device or route field checks.

## Account and engagement handoff

Three practice questions award 25 points each once, and a successful authenticated connection check awards 5 once per Europe/Zurich calendar day. Signal/Forest/Night/Track/Alpine/Dusk profile cards unlock at 0/25/75/150/300/600. Prepared marks three completed questions; 7/30/100 active-day milestones are cumulative with no streak penalty. Platform self-reports earn zero points and never imply boarding verification.

The API implements administrator-only authenticated DAU/WAU/MAU/YAU, activation, DAU/MAU stickiness and exact-day D7/D30 retention without collecting search text or location trails for engagement. Current evidence is 110 frontend unit tests / 564 assertions and 66 backend tests; the full 56-check browser suite passed in 21.3 seconds, with details maintained in [Phone QA](../../qa/README.md). Five backend response fixtures passed client validation. These checks use a fake OAuth provider and do not establish a complete human Google consent round trip.
