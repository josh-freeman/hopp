# Timetable integration

Hopp uses the public [Swiss Transport API](https://transport.opendata.ch/docs.html) at `https://transport.opendata.ch/v1`. Browser requests are plain GETs without custom headers or an API key. The upstream service enforces quotas; their exact sharing scope is undocumented.

`src/api/client.ts` implements connections, station autocomplete/coordinates, and departure stationboards. A client instance serializes requests with at least four seconds between starts, deduplicates concurrent identical requests, and caches successful responses for 30 seconds in memory. Requests, including reading their response body, time out after 12 seconds. HTTP errors, malformed responses, and HTTP-200 `errors[]` bodies are rejected. Busy responses establish a bounded cooldown; rate-limit cooldowns are at least 60 seconds. There are no hidden retry loops.

Planning requests up to six regular connections, detects the earliest supported transfer, then makes one candidate search from the main station with limit ten. The candidate query starts at the minute containing alight time plus the shortest sprint duration. It has no transport filter, so onward buses and boats remain eligible. A failed candidate search keeps the original SBB connections and fallback. Times are Unix seconds; API date/time parameters use Europe/Zurich, including date rollover.

Live refresh checks the feeder and station train boards. Feeder filters follow the actual service category (tram, bus or rail); unknown categories use an unfiltered board. Trip identity uses station, service number, destination, and **scheduled** departure; delays and platform changes never create a different identity. Callers pin the live choice using `journeyKey(selected.train)` and `refreshPlan(..., { selectedJourney, running })`. Other candidate trains remain in the result, but cannot replace the pinned recommendation. Once running, only the train board is polled.

A missing/mismatched chosen train or feeder keeps the previous freshness timestamp. Predictions and platform changes are rescored, and late feeders revalidate the fallback. A stationboard cannot validate later trains or buses in a multi-leg journey: those plans retain their previous full-journey freshness and request a full refresh. The UI must pause the countdown after 120 seconds without a successful applicable update. A passed alight stop removes the offer before running. Platform routes are desk researched, not field timed, and this API does not confirm a safe route or that a passenger boarded.

`?mock=1` and the named scenarios in `data/fixtures/scenarios.json` use **synthetic** journeys generated relative to the session/query time and perform no network requests. `missing` supplies a successful plan followed by empty stationboards for freshness tests. These example departures are not recorded SBB services. Separately, the engine fixtures in `tests/unit/fixtures/` are recovered actual responses; their README records the capture dates and source files. Recorded fixture tests also run without network access.
